# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

## 1. ภาพรวม

ฐานข้อมูลนี้แยกข้อมูลผู้แจ้งออกจากข้อมูลคำร้องเป็น 2 ตาราง โดยเชื่อมกันผ่าน `requests.requester_id` ซึ่งอ้างอิง `users.id`

```text
users                         requests
----------------------        ----------------------
id (PK)       1 ──────────<  requester_id (FK)
name                          id (PK)
department                    request_type
email                         location
                              details
                              priority
                              status
                              created_at
```

ความสัมพันธ์เป็นแบบ **หนึ่งต่อหลาย (One-to-Many)**: ผู้ใช้หนึ่งคนแจ้งคำร้องได้หลายรายการ แต่คำร้องหนึ่งรายการมีผู้แจ้งหนึ่งคน ความสัมพันธ์นี้กำหนดด้วย Foreign Key จาก `requests.requester_id` ไปยัง `users.id`

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ถ้าเก็บชื่อผู้แจ้งเป็นข้อความไว้ในทุกคำร้อง ชื่อและข้อมูลผู้ใช้จะซ้ำกัน เมื่อผู้ใช้เปลี่ยนชื่อจึงต้องแก้หลายแถว และอาจแก้ไม่ครบจนข้อมูลไม่ตรงกัน อีกทั้งการสะกดชื่อไม่เหมือนกันทำให้ค้นหาและนับคำร้องของคนเดียวกันได้ยาก

เมื่อแยกตาราง `users` เก็บข้อมูลของผู้ใช้แต่ละคนเพียงครั้งเดียว ส่วน `requests` เก็บ `requester_id` เพื่ออ้างถึงผู้ใช้ ถ้าสมชายเปลี่ยนชื่อ ก็แก้ชื่อในแถวของเขาใน `users` เพียง **1 ที่** คำร้องทุกแถวที่อ้างถึง `users.id` เดิมจะเชื่อมกับชื่อปัจจุบันได้ วิธีนี้ช่วยลดข้อมูลซ้ำและลดโอกาสที่ข้อมูลจะไม่ตรงกัน

## 3. รายละเอียดตาราง

### ตาราง `users`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | INTEGER | Primary Key, AUTOINCREMENT | เป็นเลขประจำผู้ใช้ที่ไม่ซ้ำ และให้ฐานข้อมูลสร้างเลขถัดไปโดยอัตโนมัติ |
| `name` | TEXT | NOT NULL | เก็บชื่อผู้ใช้และไม่อนุญาตให้ไม่มีชื่อ |
| `department` | TEXT | NOT NULL | ระบุภาควิชาหรือหน่วยงานเพื่อใช้ค้นหาและจัดกลุ่ม |
| `email` | TEXT | NOT NULL, UNIQUE | ต้องมีอีเมลและป้องกันการใช้อีเมลซ้ำ |

### ตาราง `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | TEXT | Primary Key | เก็บรหัสที่อ่านเข้าใจได้ เช่น `REQ-001` และต้องไม่ซ้ำ |
| `requester_id` | INTEGER | NOT NULL, Foreign Key อ้างถึง `users(id)` | เชื่อมคำร้องกับผู้แจ้งและป้องกันการอ้างถึงผู้ใช้ที่ไม่มีจริง |
| `request_type` | TEXT | NOT NULL | ระบุประเภทคำร้องและต้องมีค่า |
| `location` | TEXT | NOT NULL | ระบุตำแหน่งที่เกี่ยวข้องกับคำร้อง |
| `details` | TEXT | NOT NULL | เก็บรายละเอียดปัญหาหรือสิ่งที่ต้องการ |
| `priority` | TEXT | NOT NULL, DEFAULT `normal`, CHECK อนุญาต `low`, `normal`, `urgent` | มีค่าเริ่มต้นที่ผ่าน CHECK และจำกัดระดับความสำคัญให้เป็นค่าที่ระบบรองรับ |
| `status` | TEXT | NOT NULL, DEFAULT `pending`, CHECK อนุญาต `pending`, `in-progress`, `completed` | กำหนดค่าเริ่มต้นและป้องกันการบันทึกสถานะที่สะกดไม่ตรงกับระบบ |
| `created_at` | TEXT | NOT NULL, DEFAULT เวลาปัจจุบัน | บันทึกเวลาสร้างคำร้องโดยอัตโนมัติ |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

1.ทำไม users.id กับ requests.id ใช้ชนิดต่างกัน (INTEGER กับ TEXT)

`users.id` เป็น `INTEGER` เพราะเป็นเลขลำดับภายในฐานข้อมูลและให้ `AUTOINCREMENT` สร้างได้สะดวก ส่วน `requests.id` เป็น `TEXT` เพื่อรองรับรหัสที่อ่านได้ เช่น `REQ-001` ซึ่งมีทั้งตัวอักษรและตัวเลข

2.ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว

`CHECK` ช่วยให้ฐานข้อมูลปฏิเสธค่า `priority` หรือ `status` ที่ไม่อยู่ในรายการ แม้ API จะตรวจข้อมูลก่อนบันทึกก็ตาม เพราะข้อมูลอาจถูกเพิ่มจาก SQL โดยตรงหรือจากโปรแกรมส่วนอื่นได้ การตรวจที่ฐานข้อมูลจึงเป็นอีกชั้นที่ช่วยรักษาความถูกต้องของข้อมูล

## 5. ตัวอย่างการใช้ JOIN

คำสั่งนี้แสดงรหัสและประเภทคำร้อง พร้อมชื่อผู้แจ้งและภาควิชา โดยเชื่อม `requester_id` กับ `users.id`

```sql
SELECT r.id, r.request_type, u.name, u.department
FROM requests AS r
JOIN users AS u ON u.id = r.requester_id
ORDER BY r.id;
```

ผลลัพธ์จากข้อมูลตั้งต้นใน `schema.sql`:

| id | request_type | name | department |
|---|---|---|---|
| REQ-001 | แจ้งซ่อม | สมชาย ใจดี | วิศวกรรมซอฟต์แวร์ |
| REQ-002 | บริการบัญชีผู้ใช้ | สุภาวดี รักเรียน | วิศวกรรมซอฟต์แวร์ |
| REQ-003 | ขอใช้อุปกรณ์ | ธนกฤต ตั้งใจ | วิศวกรรมไฟฟ้า |
| REQ-004 | แจ้งซ่อม | สมชาย ใจดี | วิศวกรรมซอฟต์แวร์ |
| REQ-005 | อื่น ๆ | ปรียา ขยันยิ่ง | สำนักวิทยบริการ |
